## Abstract

FedEdge-IoT demonstrates **Federated Learning** on simulated IoT edge nodes for industrial
predictive maintenance. Multiple edge devices collaboratively train a machine condition
classifier (Normal vs Fault) using vibration sensor data, without any raw data leaving
individual nodes. The system implements **FedAvg** from scratch, compares federated against
centralized training, quantifies communication savings, and presents results through an
interactive Streamlit dashboard.

This is a **software simulation** running on a single machine — no real IoT hardware,
real sensors, or real network connections are used.

---

## Problem Statement

Industrial IoT deployments generate continuous streams of sensor data from machines.
Traditional ML for predictive maintenance requires sending all raw sensor records to a
central server, creating:

- 📶 High communication bandwidth consumption
- 🔒 Privacy and operational security risks  
- ⏱️ Latency for time-sensitive decisions
- 🌐 Single point of failure

**FedEdge-IoT** addresses these challenges using Federated Learning.

---

## Motivation and IoT Relevance

Predictive maintenance — detecting machine faults before failure — saves an estimated
\$240B annually in global industrial costs. IoT sensors make continuous monitoring possible,
but centralising all sensor data creates the challenges above.

Federated learning is already deployed in:
- Google's Gboard keyboard (learns from typed text without uploading it)
- Medical imaging (hospitals collaborate without sharing patient data)
- Automotive (vehicles learn from driving patterns without uploading routes)

This project demonstrates the same principle applied to industrial IoT.

## End-to-End Data Flow

### Federated Mode
```
1. data_generator.py creates local datasets for each node (non-IID)
2. FedAvgCoordinator broadcasts initial global_model to all nodes
3. Each EdgeNode trains locally on its PRIVATE data
4. Each EdgeNode sends model_weights (not raw data) to coordinator
5. Coordinator computes weighted average → new global_model
6. Steps 2–5 repeat for n_rounds
7. Final global_model evaluated on held-out test_set.csv
```

### Centralized Mode
```
1. data_generator.py creates the same local datasets
2. All raw records are pooled on the "server" (simulated in memory)
3. One model is trained on the combined dataset
4. Model evaluated on the same held-out test_set.csv
5. Communication bytes counted as: n_records × 80 bytes
```

## Key Concepts Explained

### IoT (Internet of Things)
A network of physical devices embedded with sensors, software, and connectivity
to collect and exchange data. Examples: smart factory machines, connected vehicles,
industrial monitoring systems.

### Edge Computing
Processing data near where it is generated (at the "edge" of the network) rather
than sending everything to a central cloud server. Reduces latency and bandwidth.

### Federated Learning
A distributed ML approach where devices train models on local data and share only
model updates with a central coordinator. Raw data never leaves the device.

### FedAvg (Federated Averaging)
The most widely used federated aggregation algorithm:

$$\mathbf{w}_{global} = \frac{\sum_{k=1}^{K} n_k \cdot \mathbf{w}_k}{\sum_{k=1}^{K} n_k}$$

Where:
- K = number of participating nodes
- n_k = local training samples at node k  
- **w**_k = local model weights after training

## Synthetic Dataset

### Feature Definitions

| Feature | Unit | Description |
|---------|------|-------------|
| `rms_vibration` | g | Root-mean-square vibration |
| `peak_vibration` | g | Peak vibration amplitude |
| `vibration_variance` | — | Vibration signal variance |
| `dominant_frequency` | Hz | Dominant FFT component |
| `temperature` | °C | Bearing temperature |
| `rpm` | RPM | Rotational speed |
| `fault` | 0/1 | **Target**: 0=Normal, 1=Fault |

### Non-IID Distribution

Each node has a different fault rate (default: 10% to 45%) and machine profile
(different RPM range and noise level). This simulates realistic heterogeneity
in industrial fleets.

### Train/Test Split

- Training: generated with seed = 42
- Test: generated with seed = 1041 (42 + 999)
- These seeds guarantee NO overlap between training and test records.

## Experiment Methodology

### Fairness guarantees
- Both models use the SAME sklearn MLPClassifier architecture (6→32→2)
- Both models use the SAME StandardScaler fitted on combined training data
- Both models are evaluated on the SAME held-out test set
- Centralized model uses the same total training data as federated (just pooled)

### What varies
- Federated: incremental training, round-by-round convergence
- Centralized: trains all data at once (max_iter=200 vs local_epochs × n_rounds)

---

## Communication Cost Methodology

### Definitions
- **Application-level bytes**: estimated payload bytes, no TCP/IP overhead
- **Float64**: 8 bytes per model parameter
- **CSV row**: ≈80 bytes per record (6 features + label + delimiters)

### Formulas

**Centralized:**
```
comm_bytes = n_training_records × 80
```

**Federated:**
```
comm_bytes = model_bytes × n_nodes × (1 + 2 × n_rounds)
             [initial broadcast + n_rounds × (upload + download)]
```

**Communication savings:**
```
savings (%) = 100 × (1 - federated_bytes / centralized_bytes)
```

## Results Interpretation

- **Accuracy gap**: Centralized often wins slightly because it trains on the full pooled dataset.
  This is the cost of data locality.
- **F1-score**: For predictive maintenance, Recall (fault detection rate) matters more than accuracy.
- **Communication savings**: The bigger the dataset and the smaller the model, the larger the savings.
- **Training time**: Federated is slower because it has multiple rounds; centralized trains once.

---

## Privacy Considerations

Federated learning provides **data locality** — raw records stay on each node.
However, it does NOT provide cryptographic privacy guarantees:

- Model weights can leak information about training data
- Gradient inversion attacks can approximately reconstruct training samples
- Membership inference attacks can determine if a record was in training

**Not implemented:** Differential privacy, secure aggregation, homomorphic encryption.

This project is an **educational demonstration** of communication efficiency and data locality.
